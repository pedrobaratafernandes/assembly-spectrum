# Capítulo Oito - Sprites

## Converter Posições de Píxeis em Endereços de Ecrã

Os UDGs e gráficos de caracteres são muito práticos, mas os melhores jogos costumam usar *sprites*, e não existem rotinas na ROM para nos ajudar aqui, porque Sir Clive não desenhou o Spectrum como uma máquina de jogos. Mais cedo ou mais tarde, um programador de jogos tem de confrontar a espinhosa questão da estranha organização do ecrã do Spectrum. Converter coordenadas de píxeis x e y num endereço de ecrã é um assunto complexo, mas existem alguns métodos que podemos empregar para o fazer.

### Usar uma Tabela de Procura de Endereços de Ecrã

O primeiro método consiste em usar uma tabela de endereços pré-calculados que contém o endereço de ecrã para cada uma das 192 linhas do Spectrum, como esta ou uma variação semelhante:

```assembly
    EMPTYTAP "8_prog1.tap"

    ; --- BASIC loader ---
    ORG $5D00
BasicStart:
    db 0,10
    dw Line1End-Line1Start
Line1Start:
    db $fd, $b0, $22, "32767", $22, $0d
Line1End:
    db 0,20
    dw Line2End-Line2Start
Line2Start:
    db $ef, $22, $22, $af, $0d
Line2End:
    db 0,30
    dw Line3End-Line3Start
Line3Start:
    db $f9, $c0, $b0, $22, "32768", $22, $0d
Line3End:
BasicEnd:
    SAVETAP "8_prog1.tap", BASIC, "loader", BasicStart, BasicEnd-BasicStart, 10

    ORG 32768

    DEVICE ZXSPECTRUM48
    ORG $8000

start:
    xor a               ; limpar a flag de carry e o acumulador.
    ld d,a              ; esvaziar o byte alto de de.
    ld a,(xcoord)       ; posição x.
    rla                 ; rodar à esquerda para multiplicar por 2.
    ld e,a              ; colocar no byte baixo do par de registos de.
    rl d                ; rodar o bit superior para o byte alto de de.
    ld hl,addtab        ; tabela de endereços de ecrã.
    add hl,de           ; apontar para a entrada da tabela.
    ld e,(hl)           ; byte baixo do endereço de ecrã.
    inc hl              ; apontar para o byte alto.
    ld d,(hl)           ; byte alto do endereço de ecrã.
    ld a,(ycoord)       ; posição horizontal.
    rra                 ; dividir por dois.
    rra                 ; e novamente por quatro.
    rra                 ; rodar novamente para dividir por oito.
    and 31              ; mascarar lixo rodado para os bits mais à direita.
    add a,e             ; adicionar ao endereço de início da linha.
    ld e,a              ; novo valor do registo e.
    ret                 ; retornar com o endereço do ecrã em de.

addtab: defw 16384
    defw 16640
    defw 16896
    ; ...
    ; ...



; --- Mocks para compilação autónoma ---
ycoord: defb 0
xcoord: defb 0

    SAVESNA "8_prog1.sna", start
    SAVETAP "8_prog1.tap", CODE, "8_prog1", start, $ - start, start
```

Pelo lado positivo, este método é muito rápido, mas implica ter de armazenar cada um dos 192 endereços de linha numa tabela, ocupando 384 bytes que poderiam ser melhor utilizados noutro local.

### Calcular Endereços de Ecrã

O segundo método envolve calcular o endereço nós mesmos e não requer uma tabela de procura de endereços. Ao fazê-lo, precisamos de considerar três coisas: em qual terço do ecrã o ponto está situado, a linha de caráter a que está mais próximo e a linha de píxeis em que cai dentro dessa célula. O uso criterioso do operando `and` ajudar-nos-á a decidir os três. Trata-se, no entanto, de um processo complicado, por isso peço a sua paciência enquanto tento explicar como funciona.

Podemos estabelecer em qual dos três segmentos do ecrã um ponto está situado pegando na coordenada vertical e mascarando os seis bits menos significativos para deixar um valor de 0, 64 ou 128, estando cada um dos segmentos a 64 píxeis de distância. Como os bytes altos dos endereços dos 3 segmentos do ecrã são 64, 72 e 80 – uma diferença de 8 ao passar de um segmento para outro – pegamos neste valor mascarado e dividimo-lo por 8 para obter um valor de 0, 8 ou 16. Em seguida, adicionamos 64 para obter o byte alto do segmento do ecrã.

Cada segmento está dividido em 8 posições de células de caráter que estão separadas por 32 bytes, por isso, para encontrar esse aspeto do nosso endereço, pegamos na coordenada vertical e mascaramos os dois bits mais significativos que utilizámos para determinar o segmento, juntamente com os três bits menos significativos que determinam a posição do píxel. A instrução `and 56` servirá perfeitamente. Isto dá-nos a posição da célula de caráter como um múltiplo de 8, e como as linhas de caracteres estão separadas por 32 bytes, multiplicamos este valor por 4 e colocamos o nosso número no byte baixo do endereço do ecrã.

Finalmente, as células de caracteres são subdivididas em linhas de píxeis com 256 bytes de distância, pelo que pegamos novamente na nossa coordenada vertical, mascaramos tudo exceto os bits que determinam a linha usando `and 7` e adicionamos o resultado ao byte alto. Isso dar-nos-á o nosso endereço de ecrã vertical. A partir daí, pegamos na nossa coordenada horizontal, dividimo-la por 8 e adicionamo-la ao nosso endereço.

Aqui está uma rotina que retorna o endereço do ecrã para `(xcoord, ycoord)` no par de registos `de`. Poderia facilmente ser modificada para retornar o endereço nos registos `hl` ou `bc`, se desejado.

```assembly
    EMPTYTAP "8_prog2.tap"

    ; --- BASIC loader ---
    ORG $5D00
BasicStart:
    db 0,10
    dw Line1End-Line1Start
Line1Start:
    db $fd, $b0, $22, "32767", $22, $0d
Line1End:
    db 0,20
    dw Line2End-Line2Start
Line2Start:
    db $ef, $22, $22, $af, $0d
Line2End:
    db 0,30
    dw Line3End-Line3Start
Line3Start:
    db $f9, $c0, $b0, $22, "32768", $22, $0d
Line3End:
BasicEnd:
    SAVETAP "8_prog2.tap", BASIC, "loader", BasicStart, BasicEnd-BasicStart, 10

    ORG 32768

    DEVICE ZXSPECTRUM48
    ORG $8000

start:
scadd:
    ld a,(xcoord)       ; obter coordenada vertical.
    ld e,a              ; guardar em e.

    ; Encontrar a linha dentro da célula.
    and 7               ; linha 0-7 dentro do quadrado do caráter.
    add a,64            ; 64 * 256 = 16384 = início do ecrã de visualização.
    ld d,a              ; linha * 256.

    ; Encontrar em que terço do ecrã nos encontramos.
    ld a,e              ; restaurar a vertical.
    and 192             ; segmento 0, 1 ou 2 multiplicado por 64.
    rrca
    rrca
    rrca                ; dividir por 8.
    add a,d             ; segmento 0-2 multiplicado por 8.
    ld d,a              ; adicionar a d para dar o endereço de início do segmento.

    ; Encontrar célula de caráter dentro do segmento.
    ld a,e
    rlca
    rlca
    and 224             ; 8 quadrados de caráter por segmento.
    ld e,a              ; dividir x por 8 e multiplicar por 32,
                    ; cálculo líquido: multiplicar por 4.
                    ; mascarar bits que não queremos.
                    ; cálculo da coordenada vertical terminado.

    ; Adicionar o elemento horizontal.
    ld a,(ycoord)       ; coordenada y.
    rrca
    rrca
    rrca                ; apenas precisamos de dividir por 8.
    and 31              ; quadrados de 0 a 31 ao longo do ecrã.
    add a,e             ; adicionar ao total até agora.
    ld e,a              ; de = endereço do ecrã.
    ret



; --- Mocks para compilação autónoma ---
ycoord: defb 0
xcoord: defb 0

    SAVESNA "8_prog2.sna", start
    SAVETAP "8_prog2.tap", CODE, "8_prog2", start, $ - start, start
```

## Deslocamento

Depois de o endereço ser estabelecido, precisamos de considerar como os nossos gráficos são deslocados para a sua posição. Os três bits mais baixos da coordenada horizontal indicam quantos deslocamentos de píxeis são necessários. Uma forma lenta de desenhar (*plot*) um píxel seria chamar a rotina `scadd` acima, realizar um `and 7` na coordenada horizontal, e depois deslocar um píxel para a direita de zero a sete vezes com base no resultado, antes de o enviar para o ecrã.

Uma rotina de *sprites* com deslocamento funciona da mesma forma. A imagem gráfica é retirada da memória uma linha de cada vez, deslocada para a posição correta e depois colocada no ecrã antes de passar para a linha seguinte e repetir o processo. Poderíamos escrever uma rotina de *sprites* que calculasse o endereço de ecrã para cada linha desenhada, e de facto a primeira rotina de *sprites* que escrevi funcionava dessa maneira. Um método mais simples é determinar se nos estamos a mover dentro de uma célula de caráter, a cruzar limites de células de caracteres ou a cruzar um limite de segmento com um par de instruções `and` e incrementar ou decrementar o endereço do ecrã em conformidade. Simplificando, `and 63` retornará zero se a nova posição vertical estiver a cruzar um segmento, e `and 7` retornará zero se estiver a cruzar um limite de célula de caráter, e qualquer outra coisa significa que a nova linha está dentro da mesma célula de caráter que a linha anterior.

Esta é uma rotina de *sprites* com deslocamento que faz uso da rotina `scadd` descrita anteriormente. Para a utilizar, basta definir as coordenadas em `dispx` e `dispy`, apontar o par de registos `bc` para o gráfico do *sprite*, e chamar `sprite`.

```assembly
    EMPTYTAP "8_prog3.tap"

    ; --- BASIC loader ---
    ORG $5D00
BasicStart:
    db 0,10
    dw Line1End-Line1Start
Line1Start:
    db $fd, $b0, $22, "32767", $22, $0d
Line1End:
    db 0,20
    dw Line2End-Line2Start
Line2Start:
    db $ef, $22, $22, $af, $0d
Line2End:
    db 0,30
    dw Line3End-Line3Start
Line3Start:
    db $f9, $c0, $b0, $22, "32768", $22, $0d
Line3End:
BasicEnd:
    SAVETAP "8_prog3.tap", BASIC, "loader", BasicStart, BasicEnd-BasicStart, 10

    ORG 32768

    DEVICE ZXSPECTRUM48
    ORG $8000

start:
sprit7:
    xor 7               ; complementar os últimos 3 bits.
    inc a               ; adicionar um para dar sorte!
sprit3:
    rl d                ; rodar para a esquerda...
    rl c                ; ...para o byte do meio...
    rl e                ; ...e finalmente para a célula de caráter esquerda.
    dec a               ; contar deslocamentos efetuados.
    jr nz,sprit3        ; regressar até terminar todos os deslocamentos.

    ; A linha da imagem do sprite está agora em e + c + d, precisamos dela na forma c + d + e.
    ld a,e              ; a margem esquerda da imagem está atualmente em e.
    ld e,d              ; colocar a margem direita lá.
    ld d,c              ; a parte central vai para d.
    ld c,a              ; e a margem esquerda de volta para c.
    jr sprit0           ; concluído o ajuste, transferir para o ecrã.

sprite:
    ld a,(dispx)
    ld (tmp1),a         ; guardar a vertical.
    call scadd          ; calcular endereço do ecrã.
    ld a,16             ; altura do sprite em píxeis.
sprit1:
    ex af,af'           ; guardar o contador do ciclo.
    push de             ; guardar endereço do ecrã.
    ld c,(hl)           ; primeiro gráfico do sprite.
    inc hl              ; incrementar ponteiro para os dados do sprite.
    ld d,(hl)           ; seguinte parte da imagem do sprite.
    inc hl              ; apontar para a próxima linha de dados do sprite.
    ld (tmp0),hl        ; guardar em tmp0 para mais tarde.
    ld e,0              ; limpar o byte direito por agora.
    ld a,b              ; b contém a posição y.
    and 7               ; como estamos a cruzar as células de caracteres?
    jr z,sprit0         ; não estamos a cruzá-las, não vale a pena deslocar.
    cp 5                ; são necessários 5 ou mais deslocamentos para a direita?
    jr nc,sprit7        ; sim, deslocar a partir da esquerda porque é mais rápido.
    and a               ; limpar a flag de carry.
sprit2:
    rr c                ; rodar byte esquerdo para a direita...
    rr d                ; ...através do byte do meio...
    rr e                ; ...para o byte direito.
    dec a               ; um deslocamento a menos por fazer.
    jr nz,sprit2        ; regressar até terminar todos os deslocamentos.

sprit0:
    pop hl              ; retirar endereço do ecrã da pilha.
    ld a,(hl)           ; o que já lá está.
    xor c               ; fundir com os dados da imagem.
    ld (hl),a           ; colocar no ecrã.
    inc l               ; próxima célula de caráter para a direita.
    ld a,(hl)           ; o que já lá está.
    xor d               ; fundir com a parte central da imagem.
    ld (hl),a           ; colocar novamente no ecrã.
    inc hl              ; próxima área do ecrã.
    ld a,(hl)           ; o que já lá está.
    xor e               ; margem direita dos dados da imagem do sprite.
    ld (hl),a           ; colocar no ecrã.
    ld a,(tmp1)         ; coordenada vertical temporária.
    inc a               ; próxima linha abaixo.
    ld (tmp1),a         ; guardar nova posição.
    and 63              ; estamos a mover-nos para o terço seguinte do ecrã?
    jr z,sprit4         ; sim, então encontrar o próximo segmento.
    and 7               ; a mover-nos para a célula de caráter abaixo?
    jr z,sprit5         ; sim, encontrar a próxima linha.
    dec hl              ; recuar 2 bytes.
    dec l
    inc h               ; próxima linha desta célula de caráter.
sprit6:
    ex de,hl            ; endereço do ecrã em de.
    ld hl,(tmp0)        ; restaurar endereço do gráfico.
    ex af,af'           ; restaurar contador do ciclo.
    dec a               ; decrementar.
    jp nz,sprit1        ; se não chegou ao fim do sprite, repetir.
    ret                 ; trabalho terminado.

sprit4:
    ld de,30            ; o próximo segmento está 30 bytes à frente.
    add hl,de           ; adicionar ao endereço do ecrã.
    jp sprit6           ; regressar ao ciclo.

sprit5:
    ld de,63774         ; menos 1762.
    add hl,de           ; subtrair 1762 ao endereço físico do ecrã.
    jp sprit6           ; regressar ao ciclo.



; --- Mocks para compilação autónoma ---
tmp0: defw 0
scadd: ret
tmp1: defb 0
dispx: defb 0

    SAVESNA "8_prog3.sna", start
    SAVETAP "8_prog3.tap", CODE, "8_prog3", start, $ - start, start
```

Como pode ver, esta rotina utiliza a instrução `xor` para fundir o *sprite* no ecrã, o que funciona da mesma forma que `PRINT OVER 1` no Sinclair BASIC. O *sprite* é fundido com quaisquer gráficos já presentes no ecrã, o que pode parecer confuso. Para apagar um *sprite*, basta mostrá-lo novamente e a imagem desaparece magicamente.

Se quiséssemos desenhar um *sprite* por cima de algo que já se encontra no ecrã, precisaríamos de algumas rotinas adicionais, semelhantes à anterior. Seria necessária uma rotina para armazenar os gráficos no ecrã num buffer, para que essa parte do ecrã pudesse ser redesenhada quando o *sprite* for apagado. A rotina seguinte aplicaria uma máscara ao *sprite* para remover os píxeis à volta e por trás do *sprite* usando `and` ou `or`, e depois o *sprite* poderia finalmente ser aplicado por cima. Seria necessária outra rotina para restaurar a parte relevante do ecrã ao seu estado anterior caso o *sprite* fosse apagado. No entanto, isto consumiria muito tempo de processamento do CPU, pelo que o meu conselho seria não se preocupar com isso, a menos que o seu jogo utilize uma técnica chamada *double buffering* (duplo buffer) – também conhecida como a técnica do ecrã de fundo, ou esteja a usar *sprites* pré-deslocados, que discutiremos em breve.

Outro método que poderá querer considerar consiste em fazer com que os *sprites* pareçam passar por trás de objetos do cenário, um truque que deve ter visto em *Haunted House* ou *Egghead in Space*. Embora este método seja útil para reduzir o conflito de cores (*colour clash*), requer uma quantidade considerável de memória. Em ambos os jogos, um ecrã de máscara fictício de 6K estava localizado no endereço 24576, e cada byte de dados do *sprite* era sujeito a uma operação `and` com os dados no ecrã fictício antes de ser aplicado com `xor` no ecrã físico localizado no endereço 16384. Como o ecrã físico e o ecrã de máscara fictício estavam exatamente a 8K de distância, era possível alternar entre eles alterando o bit 5 do registo `h`. Para fazer isto na rotina de *sprites* acima, a nossa rotina `sprit0` poderia ser assim:

```assembly
    EMPTYTAP "8_prog4.tap"

    ; --- BASIC loader ---
    ORG $5D00
BasicStart:
    db 0,10
    dw Line1End-Line1Start
Line1Start:
    db $fd, $b0, $22, "32767", $22, $0d
Line1End:
    db 0,20
    dw Line2End-Line2Start
Line2Start:
    db $ef, $22, $22, $af, $0d
Line2End:
    db 0,30
    dw Line3End-Line3Start
Line3Start:
    db $f9, $c0, $b0, $22, "32768", $22, $0d
Line3End:
BasicEnd:
    SAVETAP "8_prog4.tap", BASIC, "loader", BasicStart, BasicEnd-BasicStart, 10

    ORG 32768

    DEVICE ZXSPECTRUM48
    ORG $8000

start:
sprit0:
    pop hl              ; retirar endereço do ecrã da pilha.
    set 5,h             ; endereço do ecrã fictício.
    ld a,(hl)           ; o que já lá está.
    and c               ; mascarar partes por trás do objeto.
    res 5,h             ; endereço do ecrã físico.
    xor (hl)            ; fundir os dados da imagem.
    ld (hl),a           ; colocar no ecrã.
    inc l               ; próxima célula de caráter para a direita, por favor.
    set 5,h             ; endereço do ecrã fictício.
    ld a,(hl)           ; o que já lá está.
    and d               ; mascarar com a parte central da imagem.
    res 5,h             ; endereço do ecrã físico.
    xor (hl)            ; fundir dados da imagem.
    ld (hl),a           ; colocar novamente no ecrã.
    inc hl              ; próxima secção da área do ecrã.
    set 5,h             ; endereço do ecrã fictício.
    ld a,(hl)           ; o que já lá está.
    and e               ; mascarar margem direita dos dados da imagem do sprite.
    res 5,h             ; endereço do ecrã físico.
    xor (hl)            ; fundir os dados da imagem.
    ld (hl),a           ; colocar no ecrã.
    ld a,(tmp1)         ; coordenada vertical temporária.



; --- Mocks para compilação autónoma ---
tmp1: defb 0

    SAVESNA "8_prog4.sna", start
    SAVETAP "8_prog4.tap", CODE, "8_prog4", start, $ - start, start
```

Aqui está outro método para calcular o endereço da linha seguinte para baixo. Como antes, calculamo-lo a partir do nosso endereço atual. Fazer isto é sempre bastante complicado devido à forma como o ecrã está estruturado. Na maior parte das vezes, a nossa linha seguinte está 256 bytes à frente da anterior, mas sempre que cruzamos o limite de uma célula de caráter precisamos de subtrair 1760, e ao passar de um terço do ecrã para o seguinte, precisamos de adicionar 32. Este pequeno trecho de código calcula o endereço da linha seguinte no par de registos `hl` sem corromper `de`.

```assembly
    EMPTYTAP "8_prog5.tap"

    ; --- BASIC loader ---
    ORG $5D00
BasicStart:
    db 0,10
    dw Line1End-Line1Start
Line1Start:
    db $fd, $b0, $22, "32767", $22, $0d
Line1End:
    db 0,20
    dw Line2End-Line2Start
Line2Start:
    db $ef, $22, $22, $af, $0d
Line2End:
    db 0,30
    dw Line3End-Line3Start
Line3Start:
    db $f9, $c0, $b0, $22, "32768", $22, $0d
Line3End:
BasicEnd:
    SAVETAP "8_prog5.tap", BASIC, "loader", BasicStart, BasicEnd-BasicStart, 10

    ORG 32768

    DEVICE ZXSPECTRUM48
    ORG $8000

start:
    ; Linha desenhada, agora calcular o próximo endereço de destino.
    inc h               ; incrementar píxel.
    ld a,h              ; obter endereço do píxel.
    and 7               ; a cruzar a posição do caráter?
    ret nz              ; não, já estamos na linha seguinte.
    ld a,h              ; obter endereço do píxel.
    sub 8               ; subtrair 8 para o início do segmento.
    ld h,a              ; novo byte alto do endereço.
    ld a,l              ; obter byte baixo do endereço.
    add a,32            ; uma linha abaixo.
    ld l,a              ; novo byte baixo.
    ret nc              ; ainda não chegou ao segmento seguinte.
    ld a,h              ; endereço alto.
    add a,8             ; adicionar 8 ao segmento seguinte.
    ld h,a              ; novo byte alto.


    SAVESNA "8_prog5.sna", start
    SAVETAP "8_prog5.tap", CODE, "8_prog5", start, $ - start, start
```

### Sprites Pré-deslocados

Uma rotina de *sprites* com deslocamento tem um grande inconveniente: a falta de velocidade. Deslocar todos esses dados gráficos para a posição correta leva tempo e, se o seu jogo precisar de muitos *sprites* a saltar pelo ecrã, deve considerar usar *sprites* pré-deslocados. Isto requer até oito cópias separadas da imagem do *sprite*, uma em cada uma das posições de píxeis deslocados. O mais comum é os *sprites* moverem-se em saltos de 2 píxeis, pelo que são mantidas 4 cópias do *sprite*. Trata-se depois simplesmente de calcular qual a imagem do *sprite* a utilizar com base no alinhamento horizontal do *sprite*, calcular o endereço de ecrã e copiar a imagem do *sprite* para o ecrã. Embora este método seja muito mais rápido, é fantasticamente dispendioso em termos de memória. Uma rotina de *sprites* com deslocamento requer 32 bytes para um *sprite* sem máscara de 16x16 píxeis, enquanto um *sprite* pré-deslocado com 4 posições requer 128 bytes para a mesma imagem, e para 8 posições uns incríveis 256 bytes! Escrever um jogo para o Spectrum é sempre um compromisso entre a velocidade e a memória disponível.

Poderá não querer necessariamente a mesma imagem de *sprite* em cada posição pré-deslocada. Por exemplo, alterando a posição das pernas de um *sprite* em cada uma das posições pré-deslocadas, um *sprite* pode ser animado para parecer que está a caminhar da esquerda para a direita à medida que se move pelo ecrã. Lembre-se de fazer corresponder as pernas do caráter ao número de píxeis que ele se move em cada fotograma (*frame*). Se estiver a mover um *sprite* 2 píxeis em cada fotograma, é importante fazer com que as pernas se movam 2 píxeis entre fotogramas. Menos do que isso fará com que o *sprite* pareça estar a patinar no gelo; mais do que isso e parecerá estar a lutar por tração. Revelar-lhe-ei um pequeno segredo aqui: acredite ou não, isto pode realmente afetar a jogabilidade, por isso acertar na animação é importante.

### O Método Byte Scan

Se estiver a exibir *sprites* diretamente no ecrã e desejar mostrar mais do que um par deles, poderá deparar-se rapidamente com um problema. Apagar, mover e voltar a exibir leva tempo e, enquanto isto acontece, a linha de varrimento da TV está em movimento. Se a linha de varrimento atingir o *sprite* enquanto este está a ser exibido ou apagado, poderá notar cintilação (*flicker*). Uma forma de evitar isto é usar o método *byte scan*, ou uma variação deste.

O método *byte scan* envolve desenhar o novo *sprite* enquanto apaga simultaneamente o antigo, byte a byte, ou linha a linha. Se a linha de varrimento alguma vez alcançar o seu *sprite*, a única cintilação que verá será no byte ou linha a ser desenhado nesse momento. Desta forma, não importa quantos *sprites* tem no ecrã, ou onde se encontram, porque nunca cintilam. O lado negativo é que isto pode ser difícil de implementar, envolve manter duas cópias das coordenadas de cada *sprite*, imagem, fotograma e todas as informações relevantes, e requer muitos registos. Felizmente, o Z80A tem uma instrução muito útil para alternar entre dois bancos de registos muito rapidamente: `EXX`.

Depois de chamarmos as rotinas para obter os dados gráficos do nosso *sprite* antigo em `de`, o endereço do ecrã em `hl` e talvez uma máscara em `bc`, usaríamos a instrução `exx` para os alternar para o conjunto de registos alternativo e depois chamaríamos as rotinas novamente para colocar o novo ponteiro de dados do *sprite*, endereço de ecrã e máscara nos registos `hl`, `de` e `bc`. Trata-se depois de desenhar cada linha de cada vez, calcular o endereço da linha de ecrã seguinte, alternar os registos com `exx`, desenhar a linha do novo *sprite*, calcular o endereço de ecrã seguinte e, em seguida, alternar os registos de volta. Repetido num ciclo, este processo substituirá um *sprite* sem nunca o apagar completamente do ecrã.

Não se esqueça de que ainda precisará de ter uma rotina de *sprites* simples que desenhe um *sprite* sem apagar o antigo, ou apague um *sprite* sem voltar a exibir um novo. Caso contrário, não conseguirá trazer novos *sprites* para o ecrã ou removê-los quando já não forem necessários.
