# Capítulo Treze - Duplo Buffer

Até agora, desenhámos todos os nossos gráficos diretamente no ecrã por razões de velocidade e simplicidade. No entanto, existe uma grande desvantagem neste método: se a linha de varrimento da televisão estiver a cobrir a área de ecrã específica onde estamos a apagar ou a redesenhar a nossa imagem, os nossos gráficos parecerão cintilar (*flicker*). Infelizmente, no Spectrum não existe uma forma fácil de saber onde a linha de varrimento está a cada momento, pelo que temos de encontrar uma forma de contornar este problema.

Um método que funciona bem é apagar e redesenhar todos os *sprites* imediatamente a seguir a uma instrução `halt`, antes que a linha de varrimento tenha hipótese de alcançar a imagem que está a ser desenhada. A desvantagem deste método é que o nosso código de *sprites* tem de ser bastante rápido, e mesmo assim não é aconselhável apagar e redesenhar mais do que dois *sprites* por fotograma (*frame*), porque a essa altura o varrimento já terá passado pela margem superior e entrado na área do ecrã. Claro que colocar o painel de estado no topo do ecrã poderá dar um pouco mais de tempo para desenhar os nossos gráficos e, se o jogo correr a 25 fotogramas por segundo, poderíamos empregar uma segunda instrução `halt` e manobrar outro par de *sprites* imediatamente a seguir. No entanto, chega um ponto em que isto deixa de funcionar. Se os nossos gráficos demorarem um pouco mais a desenhar, precisamos de outra forma de esconder o processo do jogador e necessitamos de empregar o uso de um segundo ecrã de buffer (*double buffering*). Isto significa que todo o trabalho de desenhar e apagar gráficos fica oculto do jogador, e tudo o que é visível é cada fotograma terminado depois de desenhado.

Existem duas formas de fazer isto no Spectrum. Um método funciona apenas numa máquina de 128K, pelo que o colocaremos de lado por enquanto. O outro método tende a ser mais complicado na prática, mas funcionará em qualquer Spectrum.

## Criar um Buffer de Ecrã

A forma mais simples de implementar o duplo buffer num Spectrum 48K é configurar um ecrã fictício noutro local da RAM e desenhar aí todos os nossos gráficos de fundo e *sprites*. Assim que o nosso ecrã estiver completo, copiamos este ecrã fictício para o ecrã físico no endereço 16384 da seguinte forma:

```assembly
    EMPTYTAP "13_prog1.tap"

    ; --- BASIC loader ---
    ORG $5D00
BasicStart:
    db 0,10
    dw Line1End-Line1Start
Line1Start:
    db $fd, $b0, $22, "32767", $22, $0d
Line1End:
    db 0,20
    dw Line2End-Line2Start
Line2Start:
    db $ef, $22, $22, $af, $0d
Line2End:
    db 0,30
    dw Line3End-Line3Start
Line3Start:
    db $f9, $c0, $b0, $22, "32768", $22, $0d
Line3End:
BasicEnd:
    SAVETAP "13_prog1.tap", BASIC, "loader", BasicStart, BasicEnd-BasicStart, 10

    ORG 32768

    DEVICE ZXSPECTRUM48
    ORG $8000

start:
    ; ...
    ; código para desenhar todos os nossos sprites etc.
    ; ...
    ; agora que o ecrã está desenhado, copiá-lo para o ecrã físico.
    ld hl,49152
    ld de,16384
    ld bc,6912
    ldir


    SAVESNA "13_prog1.sna", start
    SAVETAP "13_prog1.tap", CODE, "13_prog1", start, $ - start, start
```

Embora em teoria isto seja perfeito, na prática copiar 6912 bytes de RAM (ou 6144 bytes se ignorarmos os atributos de cor) para o ecrã a cada fotograma é demasiado lento para jogos de arcada. O segredo é reduzir a quantidade de RAM de ecrã que precisamos de copiar a cada fotograma e encontrar uma forma mais rápida do que transferi-la com a instrução `LDIR`.

A primeira forma é decidir o tamanho que o nosso ecrã vai ter. A maioria dos jogos separa o ecrã em 2 áreas: um painel de estado para exibir pontuação, vidas e outras informações, e uma janela onde toda a ação decorre. Como não precisamos de atualizar o painel de estado a cada fotograma, o nosso ecrã fictício apenas precisa de ser tão grande quanto a janela de ação. Portanto, se tivéssemos um painel de estado de 80 x 192 píxeis na margem direita do ecrã, isso deixar-nos-ia uma janela de ação de 176 x 192 píxeis, o que significa que o nosso ecrã fictício apenas precisaria de ter 22 caracteres de largura por 192 píxeis de altura, ou seja, 22 x 192 = 4224 bytes. Mover manualmente 4224 bytes de uma parte da RAM para outra é muito menos doloroso do que manipular 6114 bytes. O truque consiste em encontrar um tamanho que seja suficientemente grande para não restringir a jogabilidade, mas suficientemente pequeno para ser manipulado rapidamente. Claro que também poderemos querer tornar o nosso buffer um pouco maior nas margens. Embora estas margens não sejam exibidas no ecrã, são úteis se quisermos recortar (*clip*) os *sprites* à medida que entram na janela de ação vindo das laterais.

Assim que tivermos definido o tamanho do nosso buffer, precisamos de escrever uma rotina para o transferir para o ficheiro de exibição físico um ou dois bytes de cada vez. Ao fazê-lo, também podemos reorganizar o nosso ecrã de buffer para usar um método de exibição mais lógico do que o utilizado pelo ecrã físico. Podemos fazer concessões à organização peculiar do ficheiro de exibição do Spectrum na nossa rotina de transferência, simplificando assim quaisquer rotinas gráficas que façam uso do nosso buffer de ecrã fictício.

Existem duas formas realmente rápidas de mover um ecrã fictício para o ecrã de exibição físico. O primeiro e mais simples método consiste em utilizar muitas instruções `LDI` desenroladas. O segundo método, mais complicado, faz uso de `PUSH` e `POP` para transferir os dados.

Comecemos pelo `LDI`. Se o nosso buffer tiver 22 caracteres de largura, poderíamos transferir uma única linha do buffer para o ecrã de exibição com 22 instruções `LDI` consecutivas:

```assembly
    EMPTYTAP "13_prog2.tap"

    ; --- BASIC loader ---
    ORG $5D00
BasicStart:
    db 0,10
    dw Line1End-Line1Start
Line1Start:
    db $fd, $b0, $22, "32767", $22, $0d
Line1End:
    db 0,20
    dw Line2End-Line2Start
Line2Start:
    db $ef, $22, $22, $af, $0d
Line2End:
    db 0,30
    dw Line3End-Line3Start
Line3Start:
    db $f9, $c0, $b0, $22, "32768", $22, $0d
Line3End:
BasicEnd:
    SAVETAP "13_prog2.tap", BASIC, "loader", BasicStart, BasicEnd-BasicStart, 10

    ORG 32768

    DEVICE ZXSPECTRUM48
    ORG $8000

start:
    ldi
    ldi
    ; ... (repetir 22 vezes)


    SAVESNA "13_prog2.sna", start
    SAVETAP "13_prog2.tap", CODE, "13_prog2", start, $ - start, start
```

Como cada instrução `LDI` ocupa dois bytes de código, é evidente que tal rotina teria pelo menos o dobro do tamanho do buffer que move. Um impacto considerável quando lidamos com pouco mais de 40K de RAM útil. Em alternativa, poderá preferir mover as instruções `LDI` para uma sub-rotina que copia uma linha de píxeis, ou talvez um grupo de 8 linhas de píxeis, de cada vez. Esta rotina poderia então ser chamada a partir de um ciclo (desenrolado ou não) que se encarregaria de gerir os registos `HL` e `DE`.

O segundo método consiste em transferir o buffer para o ecrã utilizando as instruções `PUSH` e `POP`. Embora isto tenha a vantagem de ser a forma mais rápida que existe, apresenta inconvenientes. É necessário um controlo total do ponteiro da pilha (*stack pointer*), pelo que não pode ocorrer nenhuma interrupção a meio da rotina. O ponteiro da pilha deve ser guardado algures primeiro e restaurado imediatamente a seguir.

A pilha do Spectrum está normalmente localizada abaixo do código do seu programa, mas este método envolve configurar a pilha para apontar para cada parte do buffer sucessivamente e depois usar `POP` para copiar o conteúdo do buffer de ecrã fictício para cada um dos pares de registos, à vez. O ponteiro da pilha é depois movido para o ponto relevante na RAM de exibição do ecrã, antes de os registos serem enviados para a memória com `PUSH` na ordem inversa àquela em que foram retirados com `POP`. Isto é, os valores são retirados do buffer com `POP` a partir do início de cada linha, e enviados para o ecrã com `PUSH` na ordem inversa, indo do fim da linha para o início.

Abaixo está a base da rotina de transferência de ecrã de *Rallybug*. Esta utilizava um buffer de 30 caracteres de largura, com 28 caracteres visíveis no ecrã. Os 2 caracteres restantes não eram exibidos para que os *sprites* pudessem entrar no ecrã lentamente a partir da margem, em vez de aparecerem subitamente do nada. Como a largura visível do ecrã é de 28 caracteres, isto requer 14 registos de 16 bits por linha. Obviamente, o Z80A não tem tantos, mesmo contando com os registos alternativos e `IX` e `IY`.

Por este motivo, a rotina de *Rallybug* divide a visualização em duas metades de 14 bytes cada, necessitando de apenas 7 pares de registos. A rotina define o ponteiro da pilha para o início de cada linha do buffer por sua vez, e depois retira os dados com `POP` para `AF`, `BC`, `DE` e `HL`. Em seguida, troca estes registos para o conjunto alternativo com `EXX`, e retira mais 6 bytes com `POP` para `BC`, `DE` e `HL`. Estes registos precisam agora de ser descarregados na área do ecrã, pelo que o ponteiro da pilha é definido para apontar para o fim da linha de ecrã relevante, e `HL`, `DE` e `BC` são guardados com `PUSH`. Os registos alternativos são então restaurados, e `HL`, `DE`, `BC` e `AF` são respetivamente copiados com `PUSH` para as suas posições. Isto é repetido sucessivamente para cada metade de cada linha de ecrã, antes de o ponteiro da pilha ser restaurado para a sua posição original.

Complicado? Sim. Mas incrivelmente rápido.


## Deslocar o Ecrã no Buffer

Agora que temos o nosso ecrã fictício, podemos fazer-lhe o que quisermos sem o risco de cintilação ou outras anomalias gráficas, porque apenas transferimos o buffer para o ecrã físico quando terminamos de construir a imagem. Podemos colocar *sprites*, mascarados ou não, onde quisermos e na ordem que quisermos. Podemos mover o ecrã e animar os gráficos de fundo e, mais importante ainda, podemos agora deslocar o ecrã (*scroll*) em qualquer direção.

São necessárias técnicas diferentes para tipos diferentes de deslocamento, embora todos tenham um elemento em comum: como o deslocamento de ecrã é uma tarefa muito intensiva para o processador, ciclos desenrolados (*unrolled loops*) são a regra do dia. O tipo mais simples de deslocamento é um pixel para a esquerda/direita. Um deslocamento de um píxel para a direita exige que definamos o par de registos `HL` para o início do buffer e depois executemos as seguintes duas instruções repetidamente até chegarmos ao fim do buffer:

```assembly
    EMPTYTAP "13_prog4.tap"

    ; --- BASIC loader ---
    ORG $5D00
BasicStart:
    db 0,10
    dw Line1End-Line1Start
Line1Start:
    db $fd, $b0, $22, "32767", $22, $0d
Line1End:
    db 0,20
    dw Line2End-Line2Start
Line2Start:
    db $ef, $22, $22, $af, $0d
Line2End:
    db 0,30
    dw Line3End-Line3Start
Line3Start:
    db $f9, $c0, $b0, $22, "32768", $22, $0d
Line3End:
BasicEnd:
    SAVETAP "13_prog4.tap", BASIC, "loader", BasicStart, BasicEnd-BasicStart, 10

    ORG 32768

    DEVICE ZXSPECTRUM48
    ORG $8000

start:
    rr (hl)             ; rodar flag de carry e 8 bits para a direita.
    inc hl              ; próximo endereço do buffer.


    SAVESNA "13_prog4.sna", start
    SAVETAP "13_prog4.tap", CODE, "13_prog4", start, $ - start, start
```

De forma semelhante, para executar um deslocamento de um píxel para a esquerda, definimos `HL` para o último byte do buffer e executamos estas duas instruções até chegarmos ao início do buffer:

```assembly
    EMPTYTAP "13_prog5.tap"

    ; --- BASIC loader ---
    ORG $5D00
BasicStart:
    db 0,10
    dw Line1End-Line1Start
Line1Start:
    db $fd, $b0, $22, "32767", $22, $0d
Line1End:
    db 0,20
    dw Line2End-Line2Start
Line2Start:
    db $ef, $22, $22, $af, $0d
Line2End:
    db 0,30
    dw Line3End-Line3Start
Line3Start:
    db $f9, $c0, $b0, $22, "32768", $22, $0d
Line3End:
BasicEnd:
    SAVETAP "13_prog5.tap", BASIC, "loader", BasicStart, BasicEnd-BasicStart, 10

    ORG 32768

    DEVICE ZXSPECTRUM48
    ORG $8000

start:
    rl (hl)             ; rodar flag de carry e 8 bits para a esquerda.
    dec hl              ; próximo endereço do buffer.


    SAVESNA "13_prog5.sna", start
    SAVETAP "13_prog5.tap", CODE, "13_prog5", start, $ - start, start
```

Na maior parte do tempo, contudo, podemos safar-nos incrementando ou decrementando apenas o registo `L`, em vez do par `HL`, acelerando ainda mais a rotina. Isto tem a desvantagem de termos de saber exatamente quando o byte de ordem alta do endereço se altera. Por este motivo, costumo fixar o endereço do meu buffer logo no início do projeto, muitas vezes no topo da RAM, para não ter de reescrever as rotinas de deslocamento quando as coisas são movidas durante o desenvolvimento. Tal como na rotina para transferir o buffer para o ecrã físico, um ciclo desenrolado maciço é muito dispendioso em termos de RAM, pelo que é boa ideia escrever um ciclo desenrolado mais pequeno que desloque, digamos, 256 bytes de cada vez, chamando-o depois cerca de 20 vezes, dependendo do tamanho do buffer escolhido.

Além de deslocar um píxel de cada vez, também podemos deslocar quatro píxeis de forma bastante rápida. Ao substituir `rl (hl)` por `rld` no deslocamento para a esquerda, e `rr (hl)` por `rrd` no deslocamento para a direita, podemos mover 4 píxeis.

O deslocamento vertical é feito movendo bytes na RAM, de forma muito semelhante à rotina para transferir o ecrã fictício para o ecrã físico. Para deslocar um píxel para cima, definimos o nosso endereço de origem (*FROM*) como sendo o início da segunda linha de píxeis, o endereço de destino (*TO*) como o endereço do início do buffer, e copiamos os dados da origem para o destino até chegarmos ao fim do buffer. Para deslocar para baixo, temos de trabalhar na direção oposta, pelo que definimos o nosso endereço de origem (*FROM*) para o fim da penúltima linha do buffer, o nosso endereço de destino (*TO*) para o fim da última linha, e trabalhamos de trás para a frente até chegarmos ao início do buffer. A vantagem adicional do deslocamento vertical é que podemos deslocar para cima ou para baixo mais do que uma linha simplesmente alterando os endereços, e a rotina correrá exatamente à mesma velocidade. De um modo geral, não é boa ideia deslocar mais do que um píxel se a sua taxa de fotogramas for inferior a 25 fotogramas por segundo, porque o ecrã parecerá tremer (*judder*).

Existe outra técnica que pode ser empregue com o deslocamento vertical, e foi a que utilizei quando escrevi *Megablast* para a revista *Your Sinclair*. Isto envolve tratar o ecrã fictício como circular (*wraparound*). Ou seja, continua a usar a mesma quantidade de RAM para o buffer fictício, mas a parte do buffer a partir da qual começa a copiar para o topo do ecrã pode mudar de um fotograma para o seguinte. Quando atinge o fim do buffer, volta ao início. Com este sistema, a rotina para copiar o buffer obtém o endereço do início do buffer a partir de um ponteiro de 16 bits que pode apontar para qualquer linha no buffer, e copia os dados para o ecrã físico linha a linha até chegar ao fim do buffer. Neste ponto, a rotina copia os dados desde o início do buffer para a parte restante do ecrã físico. Isto torna a rotina de transferência ligeiramente mais lenta e complica quaisquer outras rotinas gráficas – que também têm de voltar à primeira linha sempre que ultrapassam a última linha do buffer. Por outro lado, significa que nenhum dado precisa de ser movido em memória para fazer o ecrã deslizar. Ao alterar o ponteiro de 16 bits para a linha que é copiada em primeiro lugar para o ecrã físico, o deslocamento é feito automaticamente quando o buffer é transferido.

## Explicação para Iniciantes: Como Funciona sob o Capô

Neste capítulo, estudámos o conceito de duplo buffer (Double Buffering) e técnicas de cópia e deslocamento (*scrolling*) de ecrã para evitar que o utilizador veja imagens a meio do desenho.

### 1. O que é o Duplo Buffer (Double Buffering)?
Desenhar gráficos diretamente no ecrã visível do Spectrum enquanto o jogo corre causa cintilação (*flicker*), porque o utilizador consegue ver o processo de eliminação e redesenho dos sprites.
*   **O Buffer Fictício (Virtual Screen)**: Para evitar isto, reservamos uma área na memória RAM normal (geralmente de 6KB) que funciona como um "ecrã invisível" ou buffer.
*   Fazemos todos os cálculos e desenhos (apagar personagens, desenhar blocos e sprites) neste buffer de RAM invisível.
*   Quando a imagem está totalmente pronta, fazemos uma cópia super rápida de todo o bloco de memória do buffer para a memória de ecrã real (`$4000-$57FF`).
*   Como a transferência é quase instantânea, o jogador apenas vê imagens estáticas perfeitas a atualizar 50 vezes por segundo, eliminando a cintilação por completo.

### 2. Copiar RAM via Instruções de Bloco (`ldi` / `ldir`)
O processador Z80 é famoso pelas suas potentes instruções de transferência de memória em bloco:
*   **`ldi` (Load and Increment)**: Copia o byte do endereço apontado por `HL` para o endereço apontado por `DE`, e depois incrementa automaticamente ambos os registos `HL` e `DE` em 1, decrementando o contador `BC` em 1.
*   **`ldir` (Load, Increment and Repeat)**: Faz exatamente o mesmo que `ldi`, mas repete o processo automaticamente até que o registo contador `BC` chegue a zero. Isto permite copiar megabytes ou kilobytes de dados com uma única linha de código, o que é ideal para transferir o ecrã virtual para o ecrã físico.
*   **Deslocamento de Bits no Scrolling (`rl` / `rr`)**: Para mover o ecrã pixel a pixel para o lado, usamos instruções como `rl (hl)` (Rotate Left) e `rr (hl)` (Rotate Right). Elas empurram os bits de cada byte do ecrã para o lado, passando o bit que sai de um byte para o byte vizinho através do Carry Flag.
